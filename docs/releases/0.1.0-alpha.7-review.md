## Installation on a phone

1. Wait for this guide to contain a real mobile-accessible download and SHA-256 tied to the final candidate. Do not use a repository filesystem path as a download link.
2. Download the named APK directly to the Android device and compare its filename and digest with the completed artifact record.
3. Open the download. If Android asks, allow the specific browser or file manager to install unknown apps, then return to the installer.
4. Confirm that the installer names the app **ASEH alpha 7 review**. After installation, open App info and confirm the version is `0.1.0-alpha.7-dev-debug` where the device exposes the full version string.
5. If Android reports a signature or update conflict for this exact package, uninstall the earlier `io.github.gilnetizen.aseh.dev.alpha7.debug` review app and install again. Uninstalling deletes that package's local ASEH state.
6. Revoke the temporary install-unknown-apps permission after installation if desired.

The intended package can coexist with the production package and with the older `io.github.gilnetizen.aseh.dev.debug` prototype. Those are separate applications with separate local data. The debug certificate is temporary, so this build does not promise future in-place upgrade continuity.

## Before each review run

- Record device model, Android/API version, phone or tablet form factor, app version, language, font scale, TalkBack state, and whether location permission is precise or approximate.
- Start from a known state. Use **Build > Delete local ASEH data** and confirm the deletion, or clear storage/uninstall the review package. Exported or printed files are outside ASEH and remain on the device or destination.
- Turn off network access or use airplane mode where location hardware remains usable. The implemented rehearsal is designed to work without an account, provider key, or network request.
- For permission-recovery coverage, begin one run with location permission ungranted. For persistence coverage, keep state for a separate force-stop/relaunch run.

## User-test walkthrough

### 1. Establish date and place in Now

1. Open **Now** and choose the device-location action rather than entering latitude or longitude.
2. Grant location permission when Android asks. Repeat the scenario with approximate permission if the device supports it.
3. Review the proposed place context before accepting it. Confirm that ASEH does not silently save a candidate.
4. Accept the candidate and inspect the local Hebrew date, sunrise, solar noon, and sunset.
5. Deny permission in a separate run and confirm that the screen gives a recoverable explanation and keeps manual place entry as an advanced fallback.
6. Follow a journey action from Now into Practice, Prayer, or Build. Record any control that is hidden off-screen, clipped, or inaccessible with TalkBack.

### 2. Complete a preparation guide

1. Open **Practice** and choose a synthetic guide.
2. Read its purpose, reasoning, uncertainty, development status, and source link.
3. Complete individual steps and save progress.
4. Leave the screen, return, and confirm that completion state persists.
5. Open its cited synthetic source and confirm that the source ID and displayed text match the guide's reference. Report any wording that implies religious approval or stable editorial status.

### 3. Exercise the workspace and configure the rehearsal in Build

1. Open **Build**. The initial Self, Household, or Qahal dashboard is a clearly labeled synthetic development fixture, not a user-created production workspace.
2. Inspect due-soon work, switch among the three workspace contexts, and exercise an available lifecycle action such as complete or reopen. Leave and return, or recreate the activity, and confirm that the action persists and the context-filtered due summary appears in **Now**.
3. Use the explicit mode control to open **Service setup**. This is the separately persisted rehearsal configuration rather than workspace-item CRUD.
4. Explicitly choose Israel or diaspora calendar region. Location alone must not make that policy choice.
5. Review the accessibility profile and set the movement, voice, and participation preferences used for this run.
6. Assign the required service leader, Torah reader, and gabbai roles.
7. Assign a primary reader to each of the seven aliyot and maftir. Review preparation state for all eight handoffs.
8. Confirm that the app says the reading passages themselves are unavailable. If you exercise manual passage planning, verify that it remains marked local and unverified.
9. Choose a device mode and output preference.

### 4. Inspect blockers and the development override

1. Before completing all setup, open **Prayer** and inspect its blockers and warnings.
2. Confirm that each missing role, reading assignment, place/date fact, or preflight item has a visible reason and a useful route back to setup.
3. Use the development-preview override once. Confirm that it permits inspection but does not mark a blocker complete or erase it from the trace.
4. Return to Build, complete the missing setup, and verify that readiness changes for the specific corrected fact.

### 5. Run the role and conductor flow

1. Complete the Prayer preflight and choose a role view.
2. Inspect the role dashboard, running order, movement/voice cues, equal-status access alternative, source trace, and include/omit/reorder reasons.
3. Start the focused conductor. Mark the current segment, advance, go back, leave the destination, and resume.
4. Confirm that unavailable liturgical text is identified as unavailable with provenance and the open decision rather than replaced with plausible-looking text.
5. Inspect all eight reading handoffs. Confirm that assignments and preparation state appear without invented Torah passages.
6. If you selected a dated weekday, Shabbat, or festival planning entry, confirm that the app keeps it separate from the fixed synthetic Shabbat-morning conductor. Occurrence-specific conductor support is not implemented.

### 6. Exercise an order change

1. In Build, change the local teaching placement option.
2. Return to Prayer and verify that only the intended optional teaching segment moves.
3. Open its explanation and confirm that the new position and the local choice are visible in the assembly trace.
4. Remove or change the choice and confirm that deterministic catalog order returns.

### 7. Review local governance and the unresolved dossier

1. Open the qahal charter template, create or edit the local draft, and review the metadata needed for local adoption.
2. Record a local adoption only after the app presents the deliberate action and scope.
3. Open the synthetic lighting/electricity dossier and inspect its competing options and unresolved status.
4. Record a local option if desired, then confirm that the dossier still says `Unresolved`; a local choice must not upgrade its evidence or editorial state.

### 8. Test Study and Ask ASEH

1. On API 37, confirm that the development pack reports **verified** and **active**. Search it with an English term, a Hebrew term, and a locator, and open a result.
2. On API 26, confirm that the pack area reports an explicit unsupported state and never claims that the pack is verified, active, or searchable.
3. Search the original installed source library, open a result, and toggle its bookmark. Confirm the bookmark survives navigation.
4. Ask a question whose answer is present verbatim in the installed synthetic corpus. Confirm that the response visibly identifies `dev.fake.installed-corpus.v1`, says it is deterministic/offline, and cites the exact source text.
5. Ask an unsupported question. Confirm that unsupported material is removed or visibly marked **Not established**, with no fabricated citation.
6. Include prompt-injection language such as a request to ignore installed sources. Confirm that it is treated as question text and does not change provider rules.
7. Ask an English high-consequence question covered by the development classifier. Confirm that the ordinary guidance path is replaced by a case-preparation response with the preserved eight-section presentation.
8. Do not interpret classifier success as substantive legal, medical, civil, denominational, or communal guidance. Record missed phrases, especially Hebrew, mixed-script, euphemistic, quoted, multi-turn, ambiguous, or urgent-danger input.

### 9. Preview, share, and print the packet

1. Generate the packet from Build or Prayer.
2. Read the disclosure and exact structured payload in the preview. Cancel once and confirm that no chooser or print service opens.
3. Preview again, choose Share, and confirm that Android's chooser receives the same reviewed text.
4. Preview again, choose Print, and use an Android print service or **Save as PDF**.
5. Compare the shared/printed content with the preview: order, assignments, readiness warnings, local choices, sources, and unavailable-content notices must agree.
6. Inspect large text, line wrapping, mixed-script order, selectable structured text, and TalkBack access. The visual PDF is not claimed to be a tagged accessible PDF; the structured text is the intended accessible equivalent.

### 10. Verify persistence and deletion

1. Force-stop ASEH and relaunch it. Confirm that the workspace, assignments, reading preparation, progress, bookmarks, choices, and conductor position recover as expected.
2. In Build, choose **Delete local ASEH data**, review the warning, cancel once, then confirm the action.
3. Revisit every destination and confirm that the retained rehearsal state returned to defaults. Device/app caches that are not user state may remain.
4. Confirm that previously shared, printed, or saved files still exist outside ASEH; the app must not claim to recall them.

- All bundled development content is original synthetic material. - `RIGHTS-001`, `RIGHTS-004`, and `LITURGY-001` remain blockers for the intended corpus and liturgical anchor. No review action in this build resolves them.
- The signed `.asehpack` is a deterministic synthetic test fixture, not approved liturgy or a release corpus. - Workspace dashboards begin from a labeled synthetic fixture and persist fixture lifecycle commands. General user-created workspace/item CRUD is not implemented.

- Staging and production flavors contain no development catalog and cannot demonstrate this walkthrough.

## Privacy and network expectations

The review build requires no account or telemetry and the fake Study provider is offline. Device location is requested as a foreground, one-shot input and retained locally only after the user's confirmation through the place-context flow. The packet leaves ASEH only after preview and an explicit Share or Print action. Reviewers should stop and report the build if it attempts an unexplained network request, logs sensitive case material, exports without a preview, or claims deletion of files already handed to another app.

## Rollback, reset, and uninstall

- To reset the rehearsal while keeping the app installed, use **Build > Delete local ASEH data** and confirm. Android **Settings > Apps > ASEH alpha 7 review > Storage > Clear storage** is the device-level fallback.
- To remove the review build, use Android App info and choose **Uninstall** for package `io.github.gilnetizen.aseh.dev.alpha7.debug`.
- Android backup is disabled for ASEH; uninstalling removes this package's internal state. Export any packet you intend to keep first.
- Shared documents, saved PDFs, print-service files, and screenshots are outside ASEH and are not removed by reset or uninstall.
- The old `io.github.gilnetizen.aseh.dev.debug` prototype and the new review package are separate. Remove each individually if both appear.
- A future review APK signed with a different debug certificate may require uninstall/reinstall and therefore local-data loss. This development channel does not promise durable upgrade migration.
- Public Android rollback normally uses a newly versioned, correctly signed forward-fix under `RELEASE.md`. This unsigned/unpublished review process is not a public rollback channel.

## Stop and report

Stop the walkthrough and report the exact device, app version, step, visible message, and a screenshot when possible if any of these occur:

- the package or version differs from the completed artifact record;
- sacred, translated, transliterated, Torah, or Rambam text appears as if bundled and approved;
- a readiness blocker disappears after using only the development override;
- a local adoption changes a dossier or source from `Unresolved`/`Drafted` to an approved state;
- Ask ASEH fabricates a source, alters a cited excerpt, follows prompt-injection instructions, or gives ordinary guidance for a detected high-consequence request;
- Share or Print opens before the exact packet preview;
- deletion claims to remove a file already shared or printed;
- an unexplained network request, account prompt, provider-key request, sensitive log, crash, data-loss event, inaccessible critical control, or unusable 200%/TalkBack flow appears; or
- the saved/printed packet materially differs from the reviewed structured payload.

Send a review report with the device/API/form factor, locale, font scale, TalkBack state, precise/approximate/denied location state, exact reproduction steps, screenshots or screen recording, and whether the issue persists after a reset. Do not include sensitive case facts, credentials, or private location details.
