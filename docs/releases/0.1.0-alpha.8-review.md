## What changes in alpha.8

Alpha.8 makes two previously demonstrative areas operational:

- **Local workspace records can be maintained.** A user can rename the active Self, Household, or Qahal workspace. Household supports responsibilities, shared-calendar items, preparation kits, and nested tasks. Qahal supports local decisions, volunteer rotations and slots, inventory, and financial-control checklists. These records persist on the device, participate in due-work summaries, and open directly from global search. Deletes require confirmation, stale editors preserve newer lifecycle and child-record changes, and unreadable saved data is preserved with writes blocked until the user explicitly clears local data.
- **The selected service controls Pray.** Pray resolves a dated service occurrence from the installed development schedule and displays its service name, civil date, calendar-day classification, scheduled time, and calendar profile. A supported dated Shabbat-morning occurrence supplies the rehearsal date and local calendar context. Progress, assignments, and conductor state are keyed to the full occurrence identity, so changing dates or Israel/diaspora profiles does not overwrite another occurrence. Selecting an unsupported weekday, afternoon, or festival entry shows its metadata and an unavailable-content explanation; ASEH does not substitute the Shabbat-morning conductor or write that selection into Shabbat rehearsal progress.

The GPS-first Now flow, synthetic Practice guides, Shabbat setup and conductor, source search and bookmarks, deterministic development Ask ASEH path, signed synthetic pack path, local governance rehearsal, and packet preview/share/print flow remain available from alpha.7. Practice cards, details, sources, and saved-card controls remain available before service setup; step progress becomes writable only when a supported dated Shabbat-morning occurrence is active.

## Installation and package identity

1. Download the APK only from the completed direct link in the artifact record, then compare its SHA-256 with the recorded digest.
2. Open the download and, if Android asks, allow the specific browser or file manager to install unknown apps.
3. Confirm that Android names the app **ASEH alpha 8 review** and reports version `0.1.0-alpha.8-dev-debug` where the full version is exposed.
4. Launch the app and confirm the first screen identifies development content as synthetic where applicable.
5. Revoke the temporary install-unknown-apps permission after installation if desired.

Alpha.8 uses `io.github.gilnetizen.aseh.dev.alpha8.debug`, so it installs as a separate app from alpha.7 (`io.github.gilnetizen.aseh.dev.alpha7.debug`), the older dev prototype, and the future production package. Their local data is separate; installing alpha.8 does not migrate records from an earlier package.

The review certificate is temporary. Two APKs with this same package but different debug certificates cannot update one another. Android may require uninstalling the installed alpha.8 review app before installing bytes signed by a different runner; uninstalling deletes that package's local ASEH state.

## Database and upgrade compatibility

Alpha.8 uses operational Room schema version 5. Explicit migrations support every previously exported schema in this review package line (versions 1 through 4); destructive fallback is disabled. The v4-to-v5 migration adds the workspace snapshot store while preserving existing profile, dated-service, assignment, reading-plan, progress, bookmark, charter, and governance rows. Earlier date-only rehearsal state remains under a truthful `legacy-date:<date>` occurrence and is never attributed automatically to an Israel/diaspora profile or scheduled service.

The separate alpha.8 application ID means Android does not import alpha.7 package data during installation. Inside alpha.8, valid early workspace-review preferences are imported once into Room and removed only after durable readback. Unreadable current, recovery, or legacy payloads remain preserved with workspace writes blocked until explicit local-data clearing; they are not silently discarded or relabeled.

## Focused alpha.8 walkthrough

Run this first to verify that the new build differs materially from alpha.7.

### 1. Create household work and see it in Now

1. Open the global context control and choose **Household**.
2. Open **Build**, then choose **Workspace work** if service setup is showing.
3. Choose **Edit workspace**, replace the synthetic name with a name you recognize, and save it.
4. Under **Responsibilities**, choose **Add responsibility**. Enter a name, a due date in `YYYY-MM-DD`, and an optional local assignee. Save it.
5. Add a **Shared calendar** item. Enter a name, select its kind, set a valid start and end date, and save it.
6. Add a **Preparation kit**, then add a dated task inside it. Edit both and confirm the task remains attached to its kit.
7. Edit each new record and confirm the changed values appear. Start deleting one, cancel the confirmation, then delete it deliberately and confirm it disappears.
8. Keep a responsibility due within the current planning window, open **Now**, and confirm it appears in the Household due-work summary.
9. Force-stop and relaunch ASEH. Return to Household > Build and confirm the workspace name and retained records survive process recreation.

Expected result: these are user-created local records, not a fixed demonstration card. Invalid dates, an end date before a start date, and missing required names must not save.

### 2. Maintain qahal decisions and inventory

1. Switch the global context to **Qahal** and return to **Build > Workspace work**.
2. Rename the qahal workspace.
3. Under **Decisions**, choose **Add decision**. Enter a name, public summary, local authority or scope, classification, and optional review date, then save.
4. Confirm that the app describes this as a local operating record and makes no universal, civil, denominational, or editorial approval claim.
5. Under **Inventory**, choose **Add inventory item**. Enter a name, quantity on hand, desired minimum, and optional next-check date, then save.
6. Add a **Volunteer rotation** with a name and role, then add a dated slot inside it. Add a named **Financial-control checklist** and one control inside it; the checklist review date is optional while it remains a draft.
7. Edit the records. Confirm negative quantities, malformed dates, or an invalid date range cannot be saved.
8. Delete one of the parent records only after reviewing the confirmation that its nested items will also be removed; confirm the deletion persists after leaving and returning to Build.

Expected result: decision evidence status is not upgraded by creating a local record. Inventory and decision review dates can feed the existing due-work presentation when they fall in its planning window.

### 3. Find user records with global search

1. Create or retain a household responsibility with a distinctive two-word name.
2. Open **Search** from any primary destination and enter both words.
3. Confirm that the local Household responsibility appears before or alongside installed development-catalog results.
4. Open the result. Confirm ASEH switches to the Household context, opens **Build**, and identifies the owning workspace record.
5. Repeat with a qahal decision or inventory item, searching by a meaningful field such as its summary, scope, or name.
6. Repeat in airplane mode.

Expected result: every query term must match locally indexed text. The index is rebuilt from device-local workspace state and makes no network request.

### 4. Verify that service selection drives Pray

1. Open **Pray** and review **Choose a service**.
2. Select a dated Shabbat-morning entry supported by the installed development catalog.
3. Confirm that **Selected rehearsal occurrence** shows the service name, civil date, calendar day, scheduled time, and calendar profile.
4. Confirm that the rehearsal context below uses that occurrence's civil date and day kind. With a saved place, inspect the Hebrew-date and solar calculations for the selected date.
5. Complete one preparation or conductor item, leave Pray, return, and confirm the supported occurrence resumes its saved state.
6. Choose a dated weekday, afternoon, or other unsupported entry.
7. Confirm that its metadata remains visible under **Selected service content unavailable** and that the Shabbat conductor does not appear as though it belongs to that entry.
8. Return to the supported Shabbat-morning occurrence and confirm its rehearsal progress remains intact.

Expected result: a schedule selection is no longer a disconnected planning card. Unsupported content fails closed and cannot masquerade as the installed Shabbat-morning rehearsal.

## Broader product walkthrough

These flows remain development rehearsals, but they are interactive and persist local state.

### Now and device location

1. Open **Now** and use the device-location action; a user should not need to know latitude or longitude.
2. Grant precise or approximate foreground location permission and review the proposed place before saving it.
3. Confirm that the saved context supplies the local Hebrew date, sunrise, solar noon, and sunset.
4. Deny permission in a separate run and confirm that recovery guidance and an advanced manual fallback remain available.

### Practice

1. Open a synthetic Practice guide.
2. Read its development status, reasoning, uncertainty, and source link.
3. Open its cited source and confirm the displayed source identifier matches the guide.
4. Before a supported rehearsal occurrence exists, confirm the guide remains readable and its save-card control stays available while its step controls are disabled and explain how to finish setup.
5. In **Build > Service setup**, choose Israel or diaspora. In **Pray**, review or select the dated Shabbat-morning entry supported by the installed development catalog.
6. Return to Practice, mark steps complete, leave, and return to confirm progress persists for that occurrence.

### Service setup and conductor

1. In **Build > Service setup**, choose Israel or diaspora explicitly, configure the accessibility profile, and assign the leader, Torah reader, and gabbai.
2. Assign the seven aliyot and maftir and record reader preparation. The passages themselves must remain identified as unavailable unless an eligible reviewed pack is installed.
3. In **Pray**, inspect blockers, use the development preview if desired, complete preflight, choose a role view, and open the focused conductor.
4. Advance, go back, mark a segment complete, leave Pray, and resume.
5. Inspect the inclusion facts, source trace, embodied cues, and access alternative for a segment.

### Study and Ask ASEH

1. Search the installed synthetic source library and toggle a bookmark.
2. On supported Android versions, inspect the signed synthetic development pack and open a verified search result.
3. Ask a question whose answer is present in the synthetic corpus. Confirm the response identifies the deterministic development provider and cites installed source text.
4. Ask an unsupported question and confirm missing support is visible rather than supplied by a fabricated citation.

### Packet preview and deletion

1. Generate a rehearsal packet, inspect its disclosure and exact payload, and cancel once before invoking another app.
2. Preview again, then exercise Share or Print and compare the handed-off text with the preview.
3. Use **Build > Delete local ASEH data**, cancel once, then confirm deletion.
4. Revisit each destination and confirm local ASEH records returned to defaults. Files already shared, printed, or saved outside ASEH remain outside the deletion boundary.

## Known limits and release blockers

- **No approved prayer or Torah corpus is bundled.** The conductor supplies operational cues and unavailable-content notices, not a siddur, translation, transliteration, or Torah reading. It must not be evaluated as a complete or valid service text.
- **No real Rambam corpus is bundled.** The source library and pack are synthetic development material. `RIGHTS-001`, `RIGHTS-004`, and `LITURGY-001` remain blockers for intended corpus and liturgical content.
- **The development provider is synthetic.** `dev.fake.installed-corpus.v1` is deterministic and offline; it is not a remote model or a substitute for the source-bound AI product contract.
- **Service coverage remains narrow.** The installed conductor supports only the exact synthetic Shabbat-morning service shape. Weekday, afternoon, and festival entries expose schedule metadata and an unavailable state.
- **Workspace editing remains an initial slice.** This build does not yet provide personal-practice creation, household or qahal charter authoring, education and care programs, a document library, every service-planning object, or encrypted collaboration. Some visible records remain seeded synthetic fixtures with lifecycle controls only.
- **Hebrew UI is not reviewed.** Most visible prose is English. Hebrew locale resources use explicit English fallback copy while exercising RTL layout; this is not a reviewed Hebrew translation.
- **Staging and production fail closed.** They contain neither the development catalog/provider nor the synthetic signed pack and cannot demonstrate this walkthrough.
- **Debug upgrades are not durable.** Alpha.8 is a new package and does not import alpha.7 state. Its ephemeral debug signer can also force uninstall/reinstall between alpha.8 artifacts.
- **This is not a public release.** A complete public alpha still requires approved content, the release evidence in `docs/RELEASE.md`, protected signing, a signed tag, human approval, and the owner's final publication action.
